# Contrato futuro de rechazo recuperable

No implementado. No afecta aprobación ni contenido publicado. Estado editorial y resultado de limpieza son conceptos distintos: rebutjat puede tener cleanupPending:true.

1. Bajo exclusión de concurrencia de la solicitud, validar transición autorizada en_revisio→rebutjat y ausencia de Media relacionado que pueda ser compartido/publicado. Persistir primero rechazo, email/nombre/teléfono=null y timestamp/responsable de resolución, CONSERVANDO referencias para reintento durable. Si falla update, no borrar assets. No poner una persona ficticia como responsable de un retry automático.
2. Para cada ID referenciado, validar formato y recolectar referencias de TODAS las secciones. Solo candidato propio exclusivo; duplicados entre roles del mismo expediente se deduplican. Si aparece referencia de otra solicitud o ownership incierto, no borrar blob ni referencia; resultado blocked_shared/ownership_unknown, nunca limpieza completa. No tocar Media público ni paths arbitrarios. No adjuntar IDs a API pública.
3. Borrar asset privado seguro; inexistente cuenta como ausencia ya satisfecha. Después retirar todas sus referencias propias y persistir (principal/logo=null, galería filtra ID; al terminar []). Si delete falla, conservar referencias y devolver pending; si update posterior falla, conservar referencia durable a archivo ausente y reintentar. No afirmar atomicidad filesystem/DB.
4. Reintento automático acotado desde cron existente para rebutjat con referencias residuales; mismo guard/servicio y exclusión. Ausencia de archivo permite retirar referencia. Fallo de lectura del catálogo de referencias: fail closed. Datos legacy corruptos se bloquean con código técnico, no se inventan IDs.
5. Sin referencias ni contacto residual: segunda ejecución no escribe ni registra otro evento completed. Log por transición efectiva de limpieza de un ID/expediente, tipo/acción/timestamp/resultado/código; no email/nombre/teléfono/IP/textos/imagen/error crudo. Reintentos fallidos pueden registrar resultados distintos sin duplicar evento completed. No se promete exactly-once durable ante caída entre commit y log: requeriría mecanismo adicional no autorizado.

## Coordinación con cleaner
Antes de eliminar, mantener exclusión compartida para mutaciones de referencias y limpieza/reintento; revalidar estado y referencias dentro de ella. Guard impide asignación administrativa de refs y no permite reabrir rechazados. Creación solo refs nuevas generadas servidor. Cleaner y cleanup comparten mecanismo de exclusión, evitando snapshot obsoleto durante borrado. El lock actual por solicitud no basta por sí solo para garantía entre workers. Precondición de activación: un proceso escritor verificado; si hay varias réplicas, STOP y diseñar coordinación transaccional antes de habilitar (sin infraestructura nueva ahora). No ejecutar backfill automático de expedientes existentes sin preflight autorizado.

## Guard futuro
No eliminar guard ni autorizar writes genéricos. Distinguir creación, revisión, resolución y mantenimiento de rechazado mediante autorización interna no serializable. Create exige nombre no vacío y principal ID válido además de comprobaciones actuales. Updates activos validan estado combinado current+data; impedir que admin vacíe nombre o reponga email terminal. En rebutjat impedir reintroducción de contacto/ref desde administración; limpieza solo permite null/subconjunto de refs existentes y no muta contenido, estado ni audit de resolución. Aprovat sigue permitiendo trabajo editorial legítimo y conserva materiales; no adopta limpieza de rechazo. Sin lifecycle recursivo: servicio orquesta, middleware valida/normaliza sin llamar a update dentro de update.
