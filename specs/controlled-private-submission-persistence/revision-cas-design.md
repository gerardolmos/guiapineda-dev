# Persisted revision CAS — design only, 2026-10-18

Latest authorization permits design of one revision field per six private types, not schema/code/migration/data operations. This explicitly supersedes prerequisite FR10's earlier absolute no-schema constraint for DESIGN only. Separate017 nombre_contacto permission is not merged. All six share one contract.

## Field
Proposed Strapi integer, required:true, default:1, min:1, max:2147483647, private:true, configurable:false, not editable in Content Manager layout. Server assigns1 on accepted create; reject supplied revision on create/update rather than silently trusting it. Storage non-null is deployment target, not a claim required:true alone creates a SQL NOT NULL constraint. Installed database schema maps integer to integer; use portable signed32 positive range, below JS safe integer limit. At max, fail closed before increment; no wrap/reuse. At100 successful edits/day the range exceeds58000years; do not overengineer bigint/string transport. Zero/negative/noninteger/null are invalid once rollout completes.1 means first persisted version, first save expects1→2; no overloaded0/legacy sentinel.

Public exposure not needed. Keep schema private and transport read-only revision as authorized Admin/internal metadata, not business data. Caller may supply expectedRevision (precondition), never revision (new stored value). No extra permissions granted by knowing the number.

Chosen design explicitly plans backfill, so physical backfill required:YES. No actual records inspected or initialized. Adding a new persisted column entails physical schema rollout where absent; execution authorization remains separate. Preexisting DDL unknown. Do not treat schema default as a migration plan.

## Rollout
Maintenance window for writes to scoped types, including public create/moderation/automation during cutover (temporary availability control, no changed creation validation). Drain in-flight old workers; no mixed old/new workers. Under separately authorized migration/data gates: provision column, initialize old rows1, validate all non-null/range and counts, preserve backup. Install controlled writers and server-side expected-revision enforcement plus compatible Admin. Verify synthetic/readiness gates, then reopen writes. Old browser missing token receives428 reload-required, never bypass. No temporary legacy acceptance mode, no unsafe bypass window. Rollback before reopening can restore old deployment/data under separately authorized plan; after reopening, do not roll back to ungated writers—keep write freeze and roll forward/recover. No zero-downtime promise or deployment now.

## Transaction/CAS exact algorithm
Authenticated caller supplies original expectedRevision N and operation. Missing→428; malformed→400. BEGIN supported db.transaction callback. Load current authoritative row, compare revisionN (optional fast conflict); validate caller/transition/input and pure policy. Execute query(uid).updateMany with unique numeric id AND revision:N, data={validated parent scalars,revision:N+1,updatedAt:server now}. Never accept revision from incoming data. Exactly1→continue;0→throw409; more than1→invariant failure. This is the compare-and-set at the actual UPDATE, not the earlier read.
Then updateComponents helper and updateRelations primitive in the same ambient transaction, verify final aggregate/injected policy, reread result with revisionN+1, return; outer owner commits. Any failure throws; outer rollback removes scalar/revision/component/relation writes. No parent query.update call and no parent snapshot compensation. Revision increment is in the first parent write/reservation, not a separate final write; visible only after commit. Relation/component-only saves still issue the parent revision update. No direct join mutation may skip owner revision.

Two writers expectingN both issuing atomic conditional UPDATE(id,revisionN) cannot both commit:N→N+1 invalidates the other predicate; if provider aborts/serialization-conflicts instead of count0, return conflict/failure with zero committed writes. No vendor locking/SQL/isolation branch. If first rolls back, another may succeed fromN; at most one SUCCESSFUL commit from a given revision. Strict comparison plus no token reuse prevents ABA. This uses ordinary SQL transactional conditional-update semantics, not a runtime database test.

## What increments / no-op
Every accepted logical save increments once: scalar, components, relations, moderation, reopen, internal/automated updates and future privacy cleanup. Reads never increment. Choose simple command semantics: an accepted save with identical business payload still increments once; it represents a new accepted editor baseline. UI may omit unsent unchanged saves, but server does not promise semantic deep no-op detection. Failed or rolled-back saves never increment. Repeated request with old expectedN conflicts, not idempotent replay. A duplicate network response is handled by reload; no auto retry.

After-commit publication alone does not increment private revision. If attaching Media or updating any private association afterward, that is another controlled logical command with its own fresh baseline and increment, not a second increment of the initial approval transaction. Never back out revision after an external error.

## Admin transport / supported extension
Existing Content Manager remains the server RBAC/validation boundary. Project Admin bootstrap uses content-manager.apis.addDocumentAction(function(actions)) to wrap/replace save action ONLY for six UIDs; API found in content-manager.mjs:24+. Preserve default actions elsewhere and form validation/relation-modal semantics. Capture original revision from authorized document read metadata and store separately from mutable form values; update baseline only on successful response or explicit reload, never on background refresh while dirty. Send X-Private-Submission-Expected-Revision: N on the existing Admin save request, with ordinary business body unchanged. Same response includes new server revision metadata. Header is not a secret or authorization.
Server project request middleware for scoped authenticated Content Manager routes extracts/validates concurrency header into request-local context; documents.use routes to controlled update service and obtains context (service writers pass typed context directly). Preserve original Content Manager controller permissions/sanitized body/populate. Read middleware supplies metadata from the SAME returned document snapshot, not a second revision lookup. Schema-private revision need not appear in public API/business fields; trusted internal read response assembly retains it before public/private sanitization. Do not derive token from mutable form or server latest-read-at-save. These are future explicit project extensions, not current behavior. Old generic saves lacking context fail closed.
Conflict409: message record changed, reload required, no auto merge/retry. Null rendering and empty values remain existing Admin contract; fields can remain private read-only metadata. No Admin code touched.

## Other writers / backstop
Moderation loads revision with its action context; controlled command requires that baseline, CAS within transaction detects a race. Automation/internal service similarly declare observed revision or start a fresh operation by loading one; never retry silently with a new baseline. Public create server-only assigns1, existing required fields/token/auth unchanged. Clone/recreate not sanctioned bypass; unsupported bulk updates rejected.
Document middleware routes normal parent updates; lifecycle backstop rejects parent update/updateMany not carrying a project-owned unforgeable scoped capability. Do not permit a header to forge this capability. Framework parent single-update path disabled for six UIDs. Relations/components mutate via explicit orchestration with capability. No secondary private-parent writes in hooks: they must join an explicit command, counted once, or become a separate CAS operation after commit. Fail closed for unknown secondary writers.

## Lifecycle mapping
Timestamp beforeUpdate is replaced for scoped parent CAS by explicit server updatedAt once; createdAt preserved. before/afterUpdateMany framework hooks run inside transaction. Existing source has no six-type custom model lifecycle; existing Commerce document guard preserved/reworked as explicit authorization/transition policy rather than skipped. Component own lifecycle remains under supported helper and same transaction. Relation helper has no parent scalar lifecycle and cannot write PII; owner revision is already reserved. Privacy extension neutral now, future017 supplies sanitizer/assertion. Events/notifications that escape DB must run after awaited outer commit, never used as second corrective writes. Post-commit async code must be explicitly awaited after transaction promise resolves: installed transactionCtx.commit uses callbacks.forEach without awaiting promises, so onCommit(async...) alone cannot provide surfaced completion/errors.

## Failure/idempotency
All precommit failures rollback; no success on CAS/validation/policy/component/relation error. Network unknown→reload, no blind replay. Aftercommit failure leaves revision committed, reports completed save plus failed effect using safe codes, never a snapshot restore. Failed external effect retry is separate operation whose idempotency must be demonstrated. Millorem's retry integration remains the remaining design gate below.

## Future017 proof
Terminal cleanup plus revisionN+1 commits in one controlled write. Any editor withN conflicts even if it omits state or submits old PII. A freshN+1 writer still needs017's monotonic-null policy: revision alone is not privacy policy. Reopen increments and retains already-deleted values under017. No cleanup implemented now.
