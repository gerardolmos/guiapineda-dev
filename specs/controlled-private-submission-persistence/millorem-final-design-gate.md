## Image evidence and crash window
upload/services/image-manipulation.js:244-250 generateFileName appends crypto.randomBytes(5).toString(hex). A stable input filename therefore produces different storage hashes on repeated uploads. upload/services/upload.js:226-243 first calls uploadImage/provider.upload, THEN add(fileData). Crash/provider success before add can leave a file with no recorded Media identity; repeating creates another random name. Transaction rollback cannot reverse provider writes. DB Media record success before publication failure is recoverable only if durable identity and correct relation attachment are available; those do not cover the earlier storage-only gap. Lookup by filename is not unique or atomic. Existing source imatge link may identify a completed prior upload, but not an unrecorded storage write.

No evidence of a provider-level idempotency API was found in the inspected upload contract. Do not overwrite assets using guessed path/hash, assume local provider characteristics, or implement global orphan cleanup. A correct stable image operation key requires a supported idempotent upload/storage contract and durable reconciliation; this may exceed allowed schema/media scope.

## Transaction architecture options
A public DB create/publish in the same transaction as private approval: DB failure can roll both back if supported queries share context; does not roll back Upload provider effects. Does not establish a durable unique source key for retries/reapprove.
B commit approval then await publication function: guarantees no effect starts for failed private transaction; approved state remains if effect fails and user sees failure. But existing data cannot prove retry deduplication/concurrent uniqueness or complete image recovery. Aftercommit error must never restore private snapshot. Explicit await after transaction result, not unawaited onCommit callbacks.
C durable source-bound publication/effect identity and idempotent storage operation: promising prerequisite extension, not authorized here; cannot silently add public field/effect state/outbox.
No complete architecture selected. At-most-one public identity + idempotent retries is the desired contract, not exactly-once distributed execution.

## Required cases
1 Private transaction fails: aftercommit design prevents newly initiated publication; existing precommit upload flow must change.
2 Commit/public success: one intended publication, but concurrent at-most-one not proved.
3 Commit/public failure: keep aprovat, surface failure; safe retry not established.
4 Public success/response lost: slug lookup may recover only if unchanged; stable source mapping required.
5 Concurrent attempts: pre-read lookup does not prove exclusivity.
6 Title/slug edits: must retain identity; current key changes, so unsafe to use for recovery.
Image success/public failure, public success/image failure, retry and duplicate approval all depend on durable operation identity; no snapshot undo proposed. No publication may point to a file assumed present only because a DB transaction committed.
Reopen/reapprove should reuse existing source-bound publication without overwriting independent public editorial edits; current source has no supported reopen moderation action or immutable mapping, so this remains proposed semantics, not demonstrated behavior. No silent deletion/recreation of public documents.
